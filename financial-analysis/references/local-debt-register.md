# Локальный свод проверенного реестра обязательств

Прочитай перед арифметикой по уже проверенным договорам из БКИ и других документов. Скрипт не читает произвольный отчёт ОКБ, не определяет достоверность источников и не принимает решение о финансировании.

```sh
python <skill-dir>/scripts/summarize_debt_register.py <work-dir>/debt-register.json <work-dir>/debt-summary.json
```

Код 0 означает, что свод записей построен. Частичные и неизвестные суммы, включая расхождение итоговой сверки с принятыми записями, обозначены явно. Код 2 означает ошибку входа, нерешённое совпадение или противоречие. При структурной ошибке результат содержит `issues` с кодом `invalid_input`. При содержательном противоречии результат сохраняет доступную расшифровку, но зависимые полные суммы остаются null. Исходный JSON читается без изменения. Результат записывается атомарно в отдельный файл; путь и жёсткая ссылка на исходник запрещены.

## Подготовь вход

Схема `local-debt-register-1.0`. Корневые поля:

- `currency`: трёхбуквенный код валюты всего реестра.
- `borrower_id`: проверенный идентификатор исследуемого заёмщика.
- `report_date`: дата комплекта реестра, ГГГГ-ММ-ДД. Даты исходных записей и регулярных ориентиров не могут быть позже неё. Она не становится общей датой остатка.
- `kind`: `bki` только если аналитик подтвердил, что реестр прямых обязательств относится к БКИ с указанной датой отчёта. Значение `verified_register` по умолчанию сохраняет общий свод, но не заполняет карточки БКИ по договорным и смешанным источникам.
- `sources`: массив уникальных объектов `id`, `file`, `locator`, необязательный `kind`. Все ссылки записей, решений и платежей должны указывать на эти идентификаторы.
- `records`: массив записей. При пустом реестре для нулевого итога нужна отдельная сверка `active_obligations_review`.
- `decisions`: необязательные явные решения аналитика о совпадениях.

Одна запись:

```json
{
  "id": "A-20261020",
  "contract_id": "VERIFIED-UID-A",
  "subject_id": "BORROWER",
  "role": "borrower",
  "creditor_id": "BANK-A",
  "status": "active",
  "as_of": "2026-10-20",
  "sources": ["BKI"],
  "amounts": {
    "principal": "100.01",
    "interest": "2.02",
    "total": "102.03",
    "overdue": "0.00",
    "limit": null
  },
  "monthly_payment": {
    "amount": "10.01",
    "as_of": "2026-10-20",
    "frequency": "monthly",
    "sources": ["BKI"]
  },
  "payments": [
    {
      "id": "PAYMENT-1",
      "date": "2026-12-15",
      "amount": "40.04",
      "treatment": "replace",
      "sources": ["BKI"]
    }
  ],
  "maturity": {"date": "9999-12-31", "confirmed": false}
}
```

Суммы в заявленной валюте, неотрицательны, с двумя десятичными знаками. Допустимы JSON-числа и десятичные строки с точкой. Для денег арифметика выполняется через Decimal. Неизвестное обозначай null или отсутствующим компонентом в `amounts`, не заменяй нулём. `principal` означает основной долг, `total` общую задолженность, `interest` начисленные проценты, `overdue` просроченную задолженность, `limit` лимит. Лимит не прибавляется к долгу. Общая задолженность может содержать иные расходы, поэтому скрипт не достраивает её из двух компонентов.

`id` уникален среди записей. `contract_id` уже проверен аналитиком, скрипт не восстанавливает его по названию кредитора. `role`: `borrower`, `guarantor` или `other`. `status`: `active`, `closed` или `unknown`. Поручительства исследуемого лица и прямые долги других лиц сохраняются отдельно от прямого долга заёмщика.

`as_of` может быть null. Недатированные нули без платёжных сведений сохраняются среди проигнорированных технических записей. Недатированная содержательная запись вызывает диагностику. Она не отменяет датированный остаток. По одному проверенному договору выбирается последняя датированная запись; более старые идентификаторы сохраняются. Разные содержательные записи на последнюю дату требуют сверки. Исправь проверенный вход по оригиналу и запусти повторно. Статус unknown и положительный долг при статусе closed также требуют решения.

## Реши совпадения

Разные проверенные идентификаторы с одним кредитором автоматически не объединяются. Скрипт консервативно перечисляет такие пары в `unresolved_matches`, исключает их из подтверждённого полного итога и ждёт решения аналитика. Явно разные договоры можно сохранить решением `separate`; подтверждённые отражения одного договора объединить решением `merge`:

```json
{
  "contracts": ["VERIFIED-UID-A", "ALIAS-A"],
  "action": "merge",
  "reason": "Один УИд подтверждён на двух страницах",
  "sources": ["BKI"]
}
```

Каждое решение содержит ровно два разных известных прямых договора, действие, непустое основание и источники. Цепочки merge поддерживаются. Противоречащие решения merge и separate отклоняются. Повторный неизменённый вход даёт одинаковые байты результата. После изменения реестра аналитик повторно сверяет применимость решений по оригиналам; скрипт не подтверждает их актуальность вместо него.

## Прочитай результат

`contracts` раскрывает принятые записи, все идентификаторы обновлений, технические записи, подтверждённый срок и ошибки договора. `other_roles` содержит записи иных ролей и субъектов. `totals` отдельно показывает каждый компонент, полное `value`, `known_subtotal`, договоры и записи слагаемых, их даты и источники. Неполный подытог нельзя выдавать за полный долг. Общая сумма не рассчитывается подстановкой основного долга вместо общей задолженности.

`record_period` содержит даты последних активных записей, `source_record_period` диапазон всех датированных исходных записей. `basis` равен `sum_of_latest_records`, `common_balance_date` остаётся null. Совпадение дат нескольких записей само по себе не подтверждает сверку всего долга на эту дату.

`payment_guide.regular_monthly` содержит полное значение только при известном месячном ориентире каждого активного договора, а также известный подытог, охват и датированные записи. `includes_dated_payments: false` означает, что эта база не содержит отдельно раскрытых событий. `dated_payments` сохраняет суммы, даты, периодичность исходной базы, источники и правило учёта относительно неё. `replace` заменяет базу договора в своём месяце, `additional` добавляется сверх неё, `unknown` требует решения. Скрипт не выводит неизвестный основной долг финального платежа из других компонентов.

`monthly_payment.frequency` принимает monthly, quarterly, annual или unknown. Только датированный monthly с известной суммой передаётся в месячную базу формы. Другие частоты сохраняются в принятых записях и остаются неизвестными для этого расчёта. Общая дата окончания договора и техническая дата не становятся `monthly_until`. Даже подтверждённый срок погашения сам по себе не доказывает исполнение.

## Отрази данные кредитного отчёта

`pdf_patch` содержит `sources`, `bki` и `credit_load.contracts`. Объедини источники по id с остальным проверенным входом. Замени только соответствующие числовые поля, сохрани предмет исследования, тексты и условия нового займа. Конфликт одного id источника с разным содержанием требует сверки.

`bki` формируется только для kind bki, с датой отчёта и диапазоном принятых записей. Основной долг, общая задолженность и просрочка передаются отдельно. Если общая задолженность содержит иные расходы, необязательное поле процентов не передаётся в проверку разложения формы, а точный компонент остаётся в своде. Частичные суммы передаются как missing/null. Договорный свод вида verified_register не становится карточкой БКИ.


В расчётном результате деньги сохраняются десятичными строками. Для существующей формы числовые поля вставки преобразуются в JSON-числа только при сохранении десятичного значения. Если такое преобразование теряет точность, поле остаётся missing/null; точная сумма остаётся в своде. Макет ИП 3.2 и корпоративный макет 2.2 сохраняются.

## Общий реестр обязательств юрлица и ИП


Для новых подготовленных записей указывай:

- `obligation_type`: `bank_credit`, `nonbank_loan`, `owner_loan`, `lease`, `supplier_arrears`, `tax_arrears`, `payroll_arrears`, `advance_refund` или `other`. Это установленный вид обязательства, не предположение по названию кредитора.
- `debt_scope`: `personal`, `business`, `corporate` или `unknown`. Личные и предпринимательские долги ИП с тем же `subject_id` входят вместе. Для компании личный долг собственника сохраняется с отдельным `subject_id`; приписывать его компании через `debt_scope: personal` запрещено.
- `confirmation`: объект `status: confirmed|unverified|conflicting`, `sources`, для неподтверждённого состояния также `reason`. Неподтверждённая последняя запись остаётся вопросом и не получает полного итога. Для прежних проверенных реестров отсутствие поля означает ранее заявленную проверку; в результате это основание указано явно.
- `assumptions`: массив объектов `reason`, `sources`. Отсутствие массива сохраняется как пустой список, неизвестные суммы всё равно остаются `null`.
- `amounts.fees`: подтверждённые начисленные комиссии отдельно от основного долга, процентов и просрочки. `total` задаётся самостоятельно по источнику; сумма компонентов не достраивает неизвестный общий остаток.

Поручительство с ролью `guarantor` сохраняется отдельно. Оно входит в обязательную нагрузку только для того же заёмщика и при `guarantee_demand: {"confirmed": true, "as_of": "YYYY-MM-DD", "sources": ["ID"], "reason": "Основание требования"}`. Последняя запись с `confirmed: false` исключает прежнее требование из нагрузки; отсутствие требования не доказывает отсутствие самого поручительства. Объект `guarantees` результата сохраняет исходные строки, а `contracts[*].eligible_for_calendar` показывает допуск принятой записи. Закрытые, спорные, неподтверждённые и невызванные обязательства не становятся подтверждённым календарём.

Фактически исполненные платежи сохраняй в `record.settlements`, отдельно от будущих `payments`:

```json
{"id":"PAY-1","operation_id":"BANK-LINE-1","date":"2026-11-10","amount":"100.00","component":"principal","sources":["BANK"]}
```

`component` принимает `principal`, `interest`, `fees` или `total`. `operation_id` при наличии связывает выплату с операцией выписки. Остаток `amounts` уже относится к своей `as_of`; исторический платёж к нему не прибавляется и повторно из него не вычитается. Одно фактическое исполнение с одним `operation_id`, либо с одним `id` при отсутствии ссылки на операцию, учитывается в истории договора один раз. Разные сведения об одном исполнении сохраняют противоречие.

Подтверждённые выплаты компании за отдельного собственника помещай в корневой `owner_payments`:

```json
{"operation_id":"BANK-LINE-OWNER","subject_id":"OWNER-ID","date":"2026-11-10","amount":"30.00","sources":["BANK"],"reason":"Документально установленная выплата за собственника"}
```

Они не увеличивают долг компании. Для восстановления денежного потока последующий расчёт сверяет ссылку с фактической операцией и её классификацией, чтобы один расход не был вычтен дважды. Если выписка не представлена, сам реестр не объявляет такую сверку выполненной. Для ИП его собственные обязательства являются прямыми долгами; `owner_payments` к этому случаю не применяется.

### Сверка действующих обязательств

Если документы подтверждают, что на дату анализа у заёмщика нет действующих обязательств, добавь в корень реестра `verified_register` отдельную запись:

```json
{
  "active_obligations_review": {
    "as_of": "2026-11-17",
    "scope_complete": true,
    "no_active_obligations": true,
    "reason": "Сверены оборотно-сальдовая ведомость, договоры и расчёты с контрагентами.",
    "sources": ["TURNOVER_BALANCE", "DEBT_REVIEW"]
  }
}
```

`as_of` должна совпадать с датой файла анализа и быть не позже `report_date`. В самостоятельном запуске скрипта дата сверки сравнивается с `report_date`. В `sources` укажи объявленные в реестре документы, которые подтверждают полноту и результат сверки. Отсутствие кредитной истории в БКИ касается охвата бюро. Для вывода по всем обязательствам заёмщика нужны собственные основания.

Если полнота проверки не установлена, укажи `scope_complete: false`. Если наличие действующих обязательств не установлено, используй `no_active_obligations: null`. При подтверждённом наличии укажи `false` и внеси сами обязательства в `records`. Реестр хранит сверку и её статус. Устаревшая или неполная сверка ограничивает итог. Если отметка об отсутствии долгов расходится с принятыми записями, видны договоры и известный подытог, полный результат остаётся неизвестным. Подтверждённое отсутствие даёт нулевой остаток долга на дату сверки. Сумма доступных кредитных лимитов этим выводом не устанавливается.

### Продолжение и интерфейс последующих расчётов

`contracts` сохраняет принятую последнюю запись, `record_ids` всех версий, `settlements`, тип, сферу, подтверждённость, допущения, `inclusion_basis` и `eligible_for_calendar`. Будущий календарь использует только допущенную часть и отдельно раскрывает непринятые обязательства. `payment_guide` сохраняет известную часть и неизвестные компоненты; отсутствие полного итога не превращает их в нули. `sources`, `source_versions`, `owner_payments` и исходные записи позволяют проверить основания по сохранённым файлам. Равнозначные последние записи объединяют источники как самого обязательства, так и каждого допущения с тем же основанием. Реестр не считает исторические коэффициенты и шестимесячные сценарии.


### Части одного исторического исполнения

В `settlements` один `operation_id` может содержать отдельные `principal`, `interest` и `fees`. Одинаковая часть с той же датой и суммой из нескольких документов учитывается один раз, её `sources`, `settlement_ids` и `record_ids` объединяются. Разные суммы одного компонента или разные даты одного исполнения сохраняют `conflicting_settlement` до сверки. Реестр не складывает повторные отражения частей.

Если вместе с частями предоставлен `total`, суммируемый результат содержит один total; исходные части сохраняются в `components`. `breakdown_complete` показывает, равна ли сумма известных частей total, а `unallocated_amount` сохраняет рассчитанную разницу без присвоения ей вида долга. Сумма частей сверх total является противоречием. Исторический поток связывает результат с одним debit выписки; отсутствие такого соответствия не подменяется нулём.
